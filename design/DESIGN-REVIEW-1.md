# DESIGN-REVIEW-1 — Team Rota
2026-11-07 · convened by the pm-lead · reviewers: architect, developer (parallel, independent, fresh contexts) · inputs: design/PRODUCT-DESIGN.md v1.0, stories/ (18 stories), design/domains/*/spec.md v1.0, design/INTERFACE-REQUESTS.md

## Architect
1. design/PRODUCT-DESIGN.md, line 13 (also line 81, Permissions). Problem: J-01's outcome is that a member "can sign in", and every "own", "not own" and "forbidden" row of the Permissions table presumes an authenticated caller, yet no story, entity field or rule establishes a principal: Member has no credential (line 65), there is no sign-in action, and no spec says how an operation learns who is calling. A contract designer cannot write the security scheme of a single operation without guessing. Fix: add an identity story (US-identity-004 "Member signs in") and a rule naming the mechanism (e.g. email + password, or a session token issued by identity), and state in the Permissions preamble that every operation carries an authenticated member id supplied by identity.

2. stories/US-identity-001.md, line 8 (roles: [admin]) with design/domains/identity/spec.md line 9. Problem: the only action that creates a member requires an admin caller, so the first admin can never be created; the brief's §6 end-to-end test cannot start. Fix: add a bootstrap rule to identity (R-identity-06: "an empty team is seeded with one admin by an operator command, outside the API") and a story or a unit-level acceptance arm for it.

3. design/PRODUCT-DESIGN.md, line 67 (Week entity) with stories/US-scheduling-001.md line 11. Problem: Week has a start_date and a state but no action creates one; US-scheduling-001 says a shift "appears in the draft week" without saying whether the week pre-exists or is implied by the shift's date, and the week's first day (Monday? any date?) is undefined, so outside_week (line 13) cannot be computed. Fix: add an arm to US-scheduling-001 "a week is created for a start_date that is a Monday and begins in state draft (reason not_week_start otherwise)" or state explicitly that weeks are implicit and start_date is the Monday on or before the shift's date; either way name it in R-scheduling-01.

4. design/INTERFACE-REQUESTS.md, line 9 (end of table) with design/domains/identity/spec.md line 13 and design/domains/scheduling/spec.md line 14 (both "Interfaces this domain needs from others" sections are empty). Problem: five cross-domain reads/events exist in stories but no row requests them: identity → scheduling "does member hold an assignment in a published future week" (US-identity-003 arm 3); scheduling → identity "is member active" (US-scheduling-002 arm 1, and the transfer in US-scheduling-006); scheduling → swaps "open requests per shift" for the pending badge (US-scheduling-004 line 9, line 12); scheduling → notifications "week published" event (J-02#4, US-notifications-001); swaps → identity "is counterpart active" and member names for notification text (US-swaps-001 arm 1, US-notifications-002 arm 1). Fix: add the five rows, fill the two empty interface sections, and add "identity: active flag and names" to swaps/spec.md line 16–17.

5. stories/US-scheduling-006.md, line 12 with design/domains/swaps/spec.md line 13 (R-swaps-07) and design/PRODUCT-DESIGN.md line 70. Problem: a scheduling arm asserts that "the request is marked refused" — a write to swaps' SwapRequest from scheduling (two owners of one transition); counterpart_overlap is not in the R-swaps-07 refusal enum; US-swaps-003 arm 1 says approval first moves the request to approved, so this is an approved → refused transition absent from the state list; and whether an Approval row with decider = the planner, outcome refused, is written for a refusal the planner did not make is unstated. Fix: make approve atomic — swaps calls scheduling's transfer (row 2) before recording the approval; on overlap swaps itself records outcome refused with reason counterpart_overlap (add it to R-swaps-07's refusal enum, decider = system or the approving planner, stated), and rewrite US-scheduling-006 arm 2 to assert only scheduling's side ("transfer is refused with reason counterpart_overlap and the assignment is unchanged").

6. design/domains/swaps/spec.md, line 12 (R-swaps-06) with stories/US-swaps-004.md line 12. Problem: expired is listed as a state but no role, action or scheduler performs the transition, no clock is specified for "at the deadline", and R-swaps-03/R-swaps-04 gate on stored state only, so an accept or approve after the deadline on a stored "requested"/"accepted" row is allowed while the inbox shows "expired". If expiry is a state change, R-notifications-01 and brief §4 demand a notification that no story emits. Fix: decide and record one of two: (a) expired is derived on read from an injected clock and R-swaps-03/04 add "and before the deadline (reason past_deadline)", with no notification; or (b) a scheduled expiry job owned by swaps writes the transition and US-notifications-005 notifies requester and counterpart. Name the clock as an injected dependency in both cases so the arms are deterministic.

7. design/PRODUCT-DESIGN.md, line 77 (Roles: admin "approves swaps a planner is party to") versus line 89 (Permissions: admin "allowed (not own)") and design/domains/swaps/spec.md line 11. Problem: the Roles table scopes the admin to planner-party swaps, the Permissions table lets the admin decide any swap, and R-swaps-05 "the admin decides those" contradicts itself when the admin is a party (then nobody is named). A contract designer cannot write the authorization predicate for approve/refuse. Fix: rewrite R-swaps-05 as "any admin or planner who is not a party decides; a decision by a party is refused with party_to_swap", align line 77 to "may decide any swap they are not party to", and add an arm to US-swaps-003 for an admin deciding a non-party-planner swap (allowed or refused — choose one).

8. stories/US-identity-003.md, line 12 with design/domains/identity/spec.md line 10 and design/domains/scheduling/spec.md line 8. 9. design/PRODUCT-DESIGN.md, line 68 (Shift: date, start, end). Fix: declare start and end as time-of-day with "a shift may not cross midnight" (and a rule line), or as timestamps with "a shift belongs to the week of its start" — state it in R-scheduling-01.
