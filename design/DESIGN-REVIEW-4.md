# DESIGN-REVIEW-4 — Team Rota
2026-11-07 · convened by the pm-lead · reviewers: architect, developer (parallel, independent, fresh contexts; a workflow of two agents, structured findings graded blocking or cosmetic) · inputs: design/PRODUCT-DESIGN.md v1.3, stories/ (22 stories, 108 arms), design/domains/*/spec.md v1.3, design/INTERFACE-REQUESTS.md (IR-01..12)

## Architect
1. stories/US-notifications-004.md line 12 [BLOCKING] — Problem: Arm 2 says that on refusal 'both members receive one notification carrying the reason code, including counterpart_overlap and counterpart_inactive', and R-notifications-01 (design/domains/notifications/spec.md line 7) fixes swap_refused's recipients as 'both members'. But when the transfer is refused with counterpart_inactive the counterpart is, by definition, inactive, and R-notifications-03 (same file, line 9) says inactive members receive nothing except member_deactivated — the Notifier's IR-04 check drops them. The same clash arises whenever a decider refuses with a caller code after the counterpart was deactivated. An implementer and a test writer must choose between notifying an inactive member (breaking R-notifications-03 and US-notifications-001 arm 2's principle) and dropping them (failing arm 2 as written). The two rules cannot both hold for the case the arm itself names. Fix: Reword arm 2: 'on refusal (swap_refused) each active party receives one notification carrying the reason code, including counterpart_overlap; on counterpart_inactive, and whenever a party is inactive, only the active party is notified (R-notifications-03)'. Mirror it in R-notifications-01: 'swap_refused{…; recipients: both members, less any inactive (R-notifications-03)}'.

2. design/PRODUCT-DESIGN.md line 14 [BLOCKING] — Problem: The precedence rule settles order within a bucket as 'the order the story's arms list them' — one story. The assign operation's state refusals come from two stories: US-scheduling-002 arms 2–5 (already_assigned, overlapping_shift, shift_full, member_inactive) and US-scheduling-003 arm 4 (week_published on assign). This is not a corner case: every published week has every slot filled (publish requires it, and a transfer keeps the count), so every assign on a published shift satisfies both shift_full and week_published, both 409 state. US-scheduling-002 arm 4 expects shift_full; US-scheduling-003 arm 4 expects week_published; the rule gives no way to order arms of different stories, so two implementations answer two different codes to the same request. Create-shift and unassign are not affected (their other codes are in later buckets or the same story). Fix: State the cross-story order once. Either add to the cross-cutting refusals rule: 'a refusal about the target's own state (week_published) precedes refusals about the input, whichever story names it', or move the assign/create/unassign week_published arm into US-scheduling-002 at the head of its state arms and leave US-scheduling-003 arm 4 to publish-again only.

3. stories/US-scheduling-004.md line 11 [BLOCKING] — Problem: The board's holder-row shape cannot be written from the design without guessing. (a) Arm 1 enumerates the row as 'member id and name', but holder-request-swap 'opens the form for that assignment' (US-swaps-001 arm 8) and the request operation is keyed by assignment (R-swaps-01, IR-01, SwapRequest.assignment_id), so the row must carry the assignment id the arm omits. (b) Arm 1 says the caller's own rows 'carry holder-request-swap while now < the deadline'. The deadline is swaps' rule (R-swaps-01: 24 hours before the start instant), and 'now' is the injected clock that the cross-cutting clock rule says tests set — so the browser cannot evaluate it and the board must carry a server-computed value; yet scheduling has no interface that gives it the deadline (IR-07 returns open requests only; the 24-hour constant lives in swaps). A contract designer must choose between a per-row boolean, a per-row deadline instant compared in the browser, and nothing (browser computes from shift start) — materially different contracts, and only the first honours the clock rule. (c) The arm names one condition only; it does not say whether a row that already carries an open request (which request_open would refuse) still shows the control. Fix: Name the holder-row's fields in arm 1 and R-scheduling-05: assignment_id, member_id, name, pending (requested | accepted | absent), requestable (true only for the caller's own row on a published week while now < the deadline by the injected clock, and — state it — only when no request is open). Widen IR-07 so that swaps returns, for each assignment passed with its start instant, its open request's state and whether a new request is allowed now; the 24-hour rule then keeps one owner and scheduling never duplicates it.

4. design/PRODUCT-DESIGN.md line 119 [cosmetic] — Problem: The Permissions table has no row for 'see my own requests' (US-swaps-004, J-05#1), although the forbidden rule is defined by that table ('an action by a role the Permissions table denies'). The only sensible answer is own/own/own, since the list is scoped to the caller, so no arm's outcome changes — but the table should say it rather than leave the first action a member performs on the inbox unlisted. Fix: Add the row '| list my requests (requester or counterpart) | own | own | own |' beside 'see pending decisions'.

5. stories/US-swaps-002.md line 11 [cosmetic] — Problem: US-swaps-003 arm 2 settles that 'approve and refuse are one decide operation with an outcome'; the counterpart's answer is left open — one answer operation with an outcome (accepted | declined, reason on decline) or two operations. Both are implementable and no arm's outcome changes, but the design chose to settle the twin case and the contract designer will otherwise pick by analogy. Fix: Add to arm 1: 'accept and decline are one answer operation with an outcome; answer_reason is required on declined and absent on accepted' (mirroring US-swaps-003 arm 2), and the same phrase in R-swaps-03.

6. design/domains/scheduling/spec.md line 11 [cosmetic] — Problem: 'Lists and ties' (PRODUCT-DESIGN.md line 16) says every list names its sort key and tiebreak; the holder-rows within one shift are a list whose order neither R-scheduling-05 nor US-scheduling-004 arm 1 names. An implementation can pick, and a board comparison in a test must know it. Fix: Add to R-scheduling-05 and arm 1: 'holder-rows within a shift are ordered by assignment id ascending'.

7. design/domains/identity/spec.md line 2 [cosmetic] — Problem: All four domain specs carry the header 'v1.2 · … v1.3 applies the dispositions of DESIGN-REVIEW-3' (identity, scheduling, swaps, notifications, each line 2) while VERSIONS.md lists them at 1.3. VERSIONS.md wins, so nothing is ambiguous, but the header line is the drift VERSIONS.md says to correct at the next touch. 9. design/PRODUCT-DESIGN.md line 28 [cosmetic] — Problem: The refusal shape requires a reason and the Reason codes table claims every refusal, but two validation edges no story names have no code: (1) a body that fails shape validation (missing name/email/passcode on add, an unparseable date, decide's outcome outside approved | refused); (2) decide with outcome approved and a reason supplied — ignored or invalid_reason? Neither changes an arm's outcome and the contract can default them, but each contract refusal should carry a reason from the table. Fix: Add one generic code to the validation row, e.g. 'invalid_request (a body that fails shape or enum validation; 422)', and one clause to R-swaps-07 / US-swaps-003 arm 2: 'a reason sent with outcome approved is refused with invalid_reason' (or 'is ignored').

10. stories/US-swaps-003.md line 11 [cosmetic] — Problem: 'the response carries the decision' — the Decision alone, or the request with its decision embedded (the shape the lists of US-swaps-004 carry)? Either is fine; the contract designer should not have to pick by analogy. 11. stories/US-swaps-001.md line 30 [cosmetic] — Problem: The SwapRequest state machine has no requester-side exit: once requested or accepted, the request ends only by the counterpart's decline, a decision, or expiry — a requester who changes their mind, or who named the wrong counterpart, waits (R-swaps-02 forbids a second open request), and an accepted request on a team with no non-party active admin or planner can only expire. Nothing in the design is inconsistent, and nothing requires withdrawal; it should be a visible decision rather than an omission. Fix: If intended, add 'withdrawal or cancellation by the requester' to this story's Out of scope; if not, it is a design-change-loop item (a withdraw transition from requested, with a swap_withdrawn event to the counterpart).

12. design/domains/scheduling/spec.md line 15 [cosmetic] — Problem: R-scheduling-09: '12 active members (1 admin, 2 planners, 9 members) assigned round-robin over members in id order' — 'members' reads as either all twelve Members or the nine whose role is member; the two fixtures differ. Overlap is impossible either way and the arm is timing-tier, reported never gating, so no gate depends on it, but 'reproduces byte for byte for one seed' presumes one reading. 13. design/PRODUCT-DESIGN.md line 75 [cosmetic] — Problem: The Swap inbox screen lists swap-decline and swap-refuse but no anchor for the reason code each requires (R-swaps-07: decline unavailable | other; refusal fairness | coverage | policy | other); swap-reason is on the Swap request screen only. ## Developer
1. stories/US-swaps-001.md line 16 [BLOCKING] — Problem: counterpart_self is unreachable under the design's own precedence rule. Arm 6 lists the three counterpart checks as inactive → on_shift → self, all in the state bucket, and the Refusals rule (design/PRODUCT-DESIGN.md line 14, added in round 3) says 'within a bucket, checks run in the order the story's arms list them'. By the time the state bucket is reached, not_holder (arm 2, own/party bucket, earlier) has passed, so the requester holds a slot on that shift; a counterpart who is the requester therefore 'already holds a slot on that shift' and is answered counterpart_on_shift, never counterpart_self. R-swaps-08 (design/domains/swaps/spec.md line 14) states the conditions in a different order — active, other than the requester, holds no slot — under which self is reachable. An implementing session must choose between the arm's named outcome and the ordering rule: two different reason codes for the same input, and a test written from either fails under the other. Fix: Reorder the arm so the self check precedes the on-shift check: 'a counterpart who is the requester, is inactive, or already holds a slot on that shift is refused with reason counterpart_self, counterpart_inactive or counterpart_on_shift respectively', and align R-swaps-08 to the same order ('a member other than the requester, active, who holds no slot on that shift'). If the within-arm order is meant to be free, say so in the Refusals rule instead — but then the arm must still name which code answers the self case.

2. stories/US-notifications-004.md line 12 [BLOCKING] — Problem: Arm 2 asserts that on refusal 'both members receive one notification carrying the reason code, including counterpart_overlap and counterpart_inactive', while R-notifications-03 (design/domains/notifications/spec.md line 9) says 'inactive members receive nothing, except member_deactivated'. In the counterpart_inactive case the counterpart is inactive at emit time by definition — the path is real: a counterpart holding no future assignment is deactivated between accept and approve (US-identity-003 arm 3 permits it), the transfer is refused (US-scheduling-006 arm 3, US-swaps-003 arm 7) and swap_refused is emitted in the same transaction. The same collision arises when a decider refuses with a caller code after the counterpart was deactivated. A test of this arm that asserts a notification row for the counterpart passes under the arm and fails under R-notifications-03's 'none for inactive' test; the session must guess which is right. Fix: Rewrite arm 2: 'on refusal (swap_refused) the requester and, when still active, the counterpart receive one notification carrying the reason code (fairness, coverage, policy, other, counterpart_overlap or counterpart_inactive); with counterpart_inactive only the requester receives it, since the counterpart is inactive (R-notifications-03)'. Optionally annotate swap_refused's recipients in R-notifications-01 as 'both members (an inactive one is dropped per R-notifications-03)'.

3. design/PRODUCT-DESIGN.md line 26 [cosmetic] — Problem: The Reason codes table is introduced as 'every refusal a story names' but omits counterpart_overlap, which US-scheduling-006 arm 2 names as a refusal reason and which R-scheduling-02, R-swaps-04, R-swaps-07, IR-02 and the Decision entity (line 95) all carry. The behaviour is settled elsewhere (an internal interface refusal that surfaces only as Decision.reason and in swap_refused, never as an HTTP refusal), so no fork — but a contract designer building the reason enum from the table, or a checker of its completeness claim, would miss it. Fix: Add a row or footnote: 'internal, never an HTTP refusal: counterpart_overlap; counterpart_inactive (transfer) — surfaced as Decision.reason and in the swap_refused payload'.

4. stories/US-scheduling-004.md line 11 [cosmetic] — Problem: The holder-row's named fields are 'member id and name', yet holder-request-swap on that row 'opens the form for that assignment' (US-swaps-001 arm 8) and the request operation is keyed by assignment (SwapRequest.assignment_id), so the row must also carry the assignment id. Only one consistent reading exists, so the contract designer can derive it, but the arm and R-scheduling-05/IR-06 should say it. Fix: Write 'each holder as a holder-row with assignment id, member id and name' in arm 1 and in R-scheduling-05.

5. stories/US-scheduling-004.md line 11 [cosmetic] — Problem: 'the caller's own holder-rows of a published week carry holder-request-swap while now < the deadline' is silent on a row that already carries an open request (the server would answer request_open). The literal reading — the control is shown and the server refuses — is determinate, so no guess, but a UI that hides it would fail a literal test of this arm. Fix: Append 'and no request is open on it' (or state that the control is shown regardless and request_open is the server's answer).

6. stories/US-swaps-002.md line 11 [cosmetic] — Problem: Whether accept and decline are one answer operation with an outcome or two operations is unstated, while the analogous decide shape was settled in round 3 ('approve and refuse are one decide operation with an outcome', US-swaps-003 arm 2, R-swaps-04). Either shape satisfies every arm and the two UI controls exist regardless, so this is a contract choice, not a behaviour fork. Fix: Add to arm 1 and R-swaps-03: 'accept and decline are one answer operation with an outcome' (or 'two operations'), for symmetry with decide.

7. stories/US-scheduling-005.md line 11 [cosmetic] — Problem: 'returns only shifts the member holds, in the same order' does not say whether those shifts' holder-rows are all holders or only the caller's row. The natural reading (all holders, so the member sees who they work with) is what an implementation would pick, and a test of the arm asserts the shift set, so no arm outcome changes. Fix: Write 'returns only the shifts the member holds, each with all its holder-rows, in the same order'.

8. stories/US-swaps-003.md line 21 [cosmetic] — Problem: The §6 E2E runs 'against the real product', but the cross-cutting clock rule says 'tests set' an injected clock and names no seam by which a browser test against the deployed product sets it. Under the real clock the path still passes if the test creates a week whose shifts start more than 24 h ahead (it will not be the 'current week', so it is reached through the picker), and late-week or Sunday runs would flake if the test used the current week instead. A session can decide this without changing the arm's outcome, but the arm should say which. Fix: State in the arm: 'under the product's real clock, the E2E creates and publishes a week at least two Mondays ahead and reaches it through week-picker' — or name the clock seam the deployed product exposes to tests.

9. design/PRODUCT-DESIGN.md line 73 [cosmetic] — Problem: The week-picker anchor has no arm: round-2 A25 asked for one, the disposition added UI arms to US-scheduling-001..003 only, and US-scheduling-004 arm 4 covers list weeks at the API and board-none without naming the picker. J-03#1 'any listed week from the picker' is otherwise uncovered at the UI. Fix: Add to US-scheduling-004 arm 4: 'week-picker offers the listed weeks and selecting one shows its board'.

10. stories/US-swaps-005.md line 12 [cosmetic] — Problem: 'marked swap-party' with arm 1's 'the same list for any admin or planner' leaves open whether the API carries a per-viewer party flag (then the list differs per viewer in that field) or the list carries both parties' ids and the browser marks the row by comparing with the caller. R-swaps-09 names 'both parties' names' but not their ids. Either works and the UI test passes under both. Fix: State once: 'the list carries requester_id and counterpart_id with the names; the browser marks swap-party by comparing them with the caller' (or 'the API carries party per viewer').

11. design/domains/scheduling/spec.md line 15 [cosmetic] — Problem: R-scheduling-09's 'assigned round-robin over members in id order' can mean all 12 active Members or the 9 with role member. Both reproduce byte for byte for one seed and the timing arm measures the same 42 slots, so nothing moves; the fixture's reproducibility test is self-consistent either way. Fix: Write 'over all 12 members in id order'.

12. stories/US-scheduling-004.md line 15 [cosmetic] — Problem: The quantitative arm is complete (statistic, threshold, n, seed, tolerance, predicate, fixture, call) but its predicate has three outcomes — pass, within tolerance, red — and a test has two; whether 'within tolerance' is a passing test with a report line or a failing one is unstated. The tier never gates, so no gate outcome changes. Fix: Append 'within tolerance passes and is reported as such; red fails the timing arm'.

13. design/domains/identity/spec.md line 2 [cosmetic] — Problem: All four spec headers read 'v1.2' while the same line says 'v1.3 applies the dispositions of DESIGN-REVIEW-3', and DESIGN-REVIEW-3's gate records the specs as v1.3. A version pointer that disagrees with itself (same in scheduling, swaps and notifications spec.md line 2). Fix: Set each spec header to v1.3.

14. stories/US-identity-001.md line 8 [cosmetic] — Problem: roles: [admin] while arm 5 (line 15) is 'any signed-in caller lists the members' — a second operation with its own Permissions row (allowed for every role) that US-scheduling-002 arm 8 and US-swaps-001 arm 8 consume. The journey step bundles add and list, so nothing is guessed, but the story carries two operations and the roles field describes only one. Fix: Set roles: [admin, planner, member] with a note that arms 1–4 and 6 are admin-only, or cut list-members into its own story.

15. stories/US-swaps-003.md line 30 [cosmetic] — Problem: Data touched says 'Assignment (read through scheduling's interface)' but approval writes it through IR-02 (the transfer). Likewise US-swaps-004 line 23 and US-swaps-005 line 23 omit Shift (date, start via IR-01) and Member (names via IR-09), which their arm 1 embeds. Fix: US-swaps-003: 'Assignment (transferred through scheduling's interface, IR-02)'; US-swaps-004/005: add 'Shift (read through scheduling's interface), Member (read through identity's interface)'.
