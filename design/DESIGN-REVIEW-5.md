# DESIGN-REVIEW-5 — Team Rota
2026-11-07 · convened by the pm-lead · reviewers: architect, developer (parallel, independent, fresh contexts; a workflow of two agents, structured findings graded blocking or cosmetic) · inputs: design/PRODUCT-DESIGN.md v1.4, stories/ (22 stories, 108 arms), design/domains/*/spec.md v1.4, design/INTERFACE-REQUESTS.md (IR-01..12)

## Architect
1. design/PRODUCT-DESIGN.md line 14 [BLOCKING] — Problem: Two rules name different reason codes for one buildable input. The Refusals rule says 'A body that fails shape or enum validation is refused with reason invalid_request', and the Reason codes table (line 28) repeats it. Role is an enumeration (Entities: 'admin, planner or member'; R-identity-01) and the reason codes are enumerations (R-swaps-07), yet US-identity-001 arm 3 / US-identity-002 arm 3 answer role='foo' with invalid_role and US-swaps-001 arm 7 / US-swaps-002 arm 5 / US-swaps-003 arms 2 and 8 answer an out-of-enum reason with invalid_reason. A contract designer who types role or reason as an OpenAPI enum (the natural choice) gets framework-level enum validation that answers invalid_request before the domain can answer invalid_role / invalid_reason; one who types them as plain strings gets the story's code. The design does not say which, and both are 422 so the status does not disambiguate. Fix: Narrow the clause in the Refusals rule and in the validation row to: 'invalid_request — a body that fails shape validation, or an enum field no story names a code for (the answer's and the decision's outcome); role and the reason codes are checked by the domain and refused with the code the story names (invalid_role, invalid_reason) and are declared in the contract as strings with their values documented, not as schema enums.'

2. design/INTERFACE-REQUESTS.md line 14 [BLOCKING] — Problem: IR-07 cannot be written as a protocol without guessing its inputs. It says swaps answers, 'for each assignment scheduling passes with its holder and start instant', whether a new request 'by the holder' is allowed now '(published week, no open request, now < deadline)', with 'no re-entrant read'. Two of those three conditions need data the row does not pass: the week's state (swaps can only learn it through IR-01, which IR-07 forbids re-entering) and the caller — R-scheduling-05 (scheduling/spec.md line 11) defines requestable as 'the caller's own row on a published week' and says it is 'answered by swaps through IR-07', R-swaps-06 (swaps/spec.md line 12) says 'holder's own row', while IR-07 says 'by the holder' with no caller in the inputs. The contract unit creates this protocol's Null implementation, so its signature must be settled: either scheduling passes (assignment_id, holder_id, start_instant, week_state) plus the caller and swaps computes requestable in full, or swaps answers only 'open request's state' and 'holder may request now (no open request, now < deadline)' and scheduling applies 'published' and 'holder == caller' itself — materially different protocol shapes and a different split of the rule's ownership. Fix: Rewrite IR-07's input and output exactly, and mirror it in scheduling/spec.md line 19 and swaps/spec.md line 12: 'scheduling passes the caller's member_id and, per assignment, {assignment_id, holder_id, start_instant, week_state}; swaps returns per assignment {pending: requested | accepted | none, requestable: bool} where requestable = holder_id == caller and week_state == published and no open request and now < start_instant − 24 h; no re-entrant read'. (If the pm-lead prefers the other split, say instead that swaps returns pending and may_request_now and that scheduling ANDs published and own-row — and amend R-scheduling-05's 'both answered by swaps' accordingly.)

3. stories/US-scheduling-002.md line 14 [BLOCKING] — Problem: Two arms of this story claim the same buildable input with different codes, and the precedence rule meant to settle it is ambiguous for this pair. Input: a shift with one slot held by Mo; assign Mo again. Arm 2 ('assigning a member twice to one shift' → already_assigned) and arm 4 ('a shift whose slots are all held' → shift_full) both apply, both state/409. PRODUCT-DESIGN.md line 14 says 'a refusal about the target's own state (the week is published; the request is not in the right state) precedes refusals about the input or the counterpart … after that … in the order the story's arms list them'. 'The shift is full' reads naturally as the target's own state (→ shift_full first), while the parenthetical names only week_published and wrong_state and round 3's disposition (A2) intended plain arm order for this trio (→ already_assigned first). Nothing in v1.4 says whether the parenthetical is exhaustive. The simplest fixture for arm 2 is a one-slot shift, so a test and an implementation can disagree. Fix: Close the class in the Refusals rule: 'the target's own state means exactly the codes that say the target cannot be acted on at all — week_published, week_draft (on request) and wrong_state; every other state code follows the story's arm order'. Then the assign order is week_published → already_assigned → overlapping_shift → shift_full → member_inactive, and R-scheduling-07 can name it in its Testable-as column.

4. stories/US-swaps-002.md line 11 [cosmetic] — Problem: The decide operation settles what happens when a reason accompanies the wrong outcome (R-swaps-07, US-swaps-003 arm 2: 'any reason with outcome approve gets invalid_reason'); the answer operation does not. Arm 1 says accept records 'no answer_reason' and R-swaps-03 says answer_reason is 'absent on accepted', which describes storage, not the request. accept with reason 'unavailable' is either refused invalid_reason (by analogy) or accepted with the reason dropped. No arm builds the input, so no arm's outcome changes — cosmetic by the standard round 4 applied to the approve twin — but the contract designer should not have to pick by analogy. Fix: Add to R-swaps-03 and to US-swaps-002 arm 1 or 5 the twin clause: 'a reason sent with outcome accept is refused with invalid_reason' (or 'is ignored', if preferred — but say which).

5. stories/US-swaps-003.md line 11 [cosmetic] — Problem: 'the response is the request as the inbox lists it' — but the inbox has two list shapes: US-swaps-004 arm 1 (line 11) lists 'the other party's name' and 'the party awaited'; US-swaps-005 arm 2 lists both ids with names and a per-viewer party flag; R-swaps-09 (swaps/spec.md line 15) says 'both parties' names'. For the decider, who is neither party, 'the other party's name' is undefined, so the decide response must be the both-names shape. The create-request and answer operations name no response shape at all. Fix: Define one listed-request schema once, in R-swaps-09: {id, assignment_id, shift_date, shift_start, requester_id, requester_name, counterpart_id, counterpart_name, reason, state (the six display states), awaiting (counterpart | decider | none), answer_reason, decision {id, decider_id, outcome, reason, decided_at} or absent, party (per viewer)}; say that both lists and every swap write (request, answer, decide) return it, and change US-swaps-004 arm 1 to 'both parties' names (the screen shows the other's)'.

6. stories/US-identity-004.md line 11 [cosmetic] — Problem: Emails are unique 'compared case-insensitively' (R-identity-02, Entities) but sign-in does not say whether the email is matched case-insensitively; 'MO@EXAMPLE.TEST' against a stored 'mo@example.test' is a token or invalid_credentials. No arm asserts either; an implementer will infer case-insensitive, but it should be written. Fix: Add to arm 1 and R-identity-06: 'the email is matched case-insensitively, as R-identity-02 compares it'.

7. design/PRODUCT-DESIGN.md line 14 [cosmetic] — Problem: Validation is the last bucket, but a body whose target-identifying field fails shape (assignment_id 'abc', a start_date that is not a date, a missing member_id) cannot reach not_found, own or state checks at all — no target can be resolved — so the stated order is unsatisfiable for that input and the implementer must answer invalid_request first. No arm builds the input, and any implementation lands on the same answer, but the rule as written contradicts it. Fix: Add one clause: 'a field that identifies the target and fails shape validation is refused invalid_request at the not_found step, since nothing can be looked up; validation of the remaining body runs last'.

8. stories/US-scheduling-003.md line 12 [cosmetic] — Problem: The unfilled_slots refusal 'lists the unfilled shifts as rows of shift id, date, start and unfilled count' but names no order, while the cross-cutting rule says 'Every list names its sort key'. A test can compare as a set, so no outcome changes. Fix: Append 'in board order (date, start, then shift id)' to the arm and to R-scheduling-03.

9. design/INTERFACE-REQUESTS.md line 8 [cosmetic] — Problem: IR-01's Story column (US-swaps-001, 004, 005) and IR-09's (line 16) omit US-swaps-002 and US-swaps-003, yet both stories read the shift through IR-01 (the past_deadline arms need the start instant; the swap_accepted / swap_declined / swap_approved / swap_refused payloads need shift_date and shift_start) and names through IR-09 (counterpart_name, new_holder_name). 10. design/PRODUCT-DESIGN.md line 24 [cosmetic] — Problem: Two reason codes each sit in two buckets with two statuses: week_draft is 403 for a member's board of a draft week (line 24) and 409 for a request on a draft week (line 26); member_inactive is 403 at sign-in and 409 on assign. Per operation the status is determined, so the contract can be written; but a shared Refusal schema cannot map reason → status, and a client reading the code alone cannot tell the two situations apart. Fix: Either state under the table that the status is per operation and the contract lists each operation's own (code, status) pairs, or split the codes (e.g. board_draft 403 / week_draft 409; member_inactive 403 at sign-in / assignee_inactive 409).

11. design/INTERFACE-REQUESTS.md line 13 [cosmetic] — Problem: IR-06 asks identity for a member's 'role' for scheduling, but no scheduling rule or arm uses a member's role (the caller's role arrives through IR-11; assign checks active only; holder-rows carry name only). 13. stories/US-swaps-001.md line 30 [cosmetic] — Problem: Two reachable dead ends are fully determined by the design but worth the operator's eye, since brief §4 forbids a silent system: (1) a counterpart who is deactivated while a request is in state requested (allowed — they hold no future assignment) can neither sign in nor answer, nobody else may answer (not_counterpart), deciders may not act (wrong_state), the requester cannot withdraw (out of scope) nor re-request (request_open) until expiry, and after expiry past_deadline bars a new request — the shift cannot be handed over at all; (2) a swap_accepted whose eligible-decider set is empty (every admin and planner is a party) shows the requester 'awaiting decider' with nobody to decide. ## Developer
1. design/PRODUCT-DESIGN.md line 14 [BLOCKING] — Problem: The Refusals rule says 'A body that fails shape or enum validation is refused with reason invalid_request' (repeated in the Reason codes table, line 28). Role is an enumeration (admin, planner, member) and every reason code is an enumeration, and a missing reason is a shape failure if the contract marks the field required — so on the input {role: "foo"} the rule answers invalid_request while US-identity-001 arm 3 and US-identity-002 arm 3 answer invalid_role; on {reason: "foo"} the rule answers invalid_request while US-swaps-001 arm 7, US-swaps-002 arm 5 and US-swaps-003 arm 8 answer invalid_reason; on a body with no reason the rule (required field) answers invalid_request while the arms answer reason_required. All sit in the validation bucket, and the within-bucket tie-break ('the order the story's arms list them') cannot settle it because invalid_request appears in no arm. A contract designer must choose between typing role and reason as enums in the schema (the framework answers invalid_request before the domain runs) and typing them as strings with the domain enumerating (the domain answers invalid_role / invalid_reason / reason_required): two contracts, two reason codes for one input a test builds. Fix: Narrow invalid_request and settle precedence in the same sentence: 'invalid_request covers only a body that cannot be read into the operation's fields — a missing or wrong-typed field, or an outcome outside accept | decline and approve | refuse; a validation code a story names (invalid_role, reason_required, invalid_reason, not_week_start, outside_week, invalid_interval, invalid_slots) is always the answer for its field, so the contract carries role and the reason codes as strings and the domain enumerates them.' Apply the same parenthetical in the Reason codes table (line 28).

2. design/PRODUCT-DESIGN.md line 14 [BLOCKING] — Problem: The v1.4 sentence 'a refusal about the target's own state (the week is published; the request is not in the right state) precedes refusals about the input or the counterpart, whichever story names it' defines the category by a dichotomy — the target versus the input or the counterpart — and shift_full is a fact about the target shift, not about the input member. Read by that dichotomy, shift_full precedes already_assigned and overlapping_shift on the assign operation; read by the arm order of US-scheduling-002 (lines 12–14), it follows them. The two readings diverge on a one-slot shift whose holder is assigned again — the minimal fixture for the already_assigned arm — answering already_assigned under one and shift_full under the other. Round 3 settled this pair by arm order; round-4 disposition A2 named '(week_published)' explicitly, and the applied text generalised it into a description a fresh session cannot pin to codes. Fix: Name the codes instead of describing them: 'Within the state bucket, exactly week_published and wrong_state precede every other state code, whichever story names them; after that, checks run in the order the story's arms list them.' This keeps the cross-story order round 4 needed (week_published before shift_full on a published shift) and the arm order round 3 settled (already_assigned, overlapping_shift, shift_full, member_inactive).

3. design/INTERFACE-REQUESTS.md line 14 [cosmetic] — Problem: IR-07 asks swaps to answer 'whether a new request by the holder is allowed now (published week, no open request, now < deadline)' with 'no re-entrant read', but scheduling passes only the assignment with its holder and start instant — swaps cannot see the week's state; and R-scheduling-05 (scheduling spec line 11) says requestable means 'the caller's own row', which IR-07 also lacks the caller to evaluate. Either scheduling passes the week's state and ANDs caller == holder itself, or swaps answers only 'no open request and now < deadline' and scheduling applies the published-week and own-row conditions. Both give the same board, so no arm's outcome changes, but the protocol signature the architect writes into INTERFACES.md differs. Fix: State in IR-07 which side evaluates each condition: 'scheduling passes {assignment_id, holder_id, start_instant}; swaps returns {pending: requested | accepted | none, allowed: no open request and now < the deadline}; scheduling sets requestable = allowed and week published and holder == caller'. Mirror the split in R-scheduling-05 and R-swaps-06.

4. stories/US-swaps-003.md line 11 [cosmetic] — Problem: Arm 1 says the decide response is 'the request as the inbox lists it', but the inbox carries two differently shaped rows: US-swaps-004 arm 1 (line 11) lists 'the other party's name', the party awaited and a state that may read expired, while US-swaps-005 arm 2 lists requester_id, counterpart_id, both names and a per-viewer party flag; R-swaps-09 (swaps spec line 15) says 'both parties' names'. US-swaps-001 and US-swaps-002 do not say what the request and answer operations return at all, and whether expired appears in the state field or beside it is unstated. A contract designer can settle all of this without changing any arm's outcome, but is currently settling it by analogy. Fix: Define one request row once in R-swaps-09 — {id, assignment_id, shift date, shift start, requester_id, requester name, counterpart_id, counterpart name, reason, state (as displayed: expired included), created_at, answered_at, answer_reason, decision, awaiting} — returned by request, answer and decide and listed by US-swaps-004; the pending list of US-swaps-005 is the same row plus party. Change US-swaps-004 arm 1 from 'the other party's name' to 'both parties' names' to match the rule.

5. design/domains/swaps/spec.md line 9 [cosmetic] — Problem: R-swaps-03 and US-swaps-002 arm 1 say answer_reason is 'required on declined, absent on accepted', but do not say what an accept that carries an answer_reason gets — ignored, or invalid_reason. R-swaps-07 settles the twin case for decide ('any reason with outcome approve gets invalid_reason'), so the answer operation's silence is an asymmetry the contract designer will fill by analogy. No arm's outcome changes. Fix: Add to R-swaps-03 and US-swaps-002 arm 5 the clause that mirrors R-swaps-07: 'an answer_reason sent with outcome accept is refused with invalid_reason' (or state that it is ignored).

6. design/domains/scheduling/spec.md line 15 [cosmetic] — Problem: R-scheduling-09 fixes the fixture's shape and says it 'reproduces byte for byte for one seed', but two details that fix which member holds which assignment id are unstated: the order in which the 42 slots are walked for the round-robin (by date, then start, then slot index is implied, not written), and whether the first of the five open requests is requested or accepted ('alternating requested and accepted'). Every walk gives no overlap because the three shifts are adjacent half-open intervals, and the timing arm's outcome does not depend on it, so nothing moves — but the reproduction test presumes one reading. Fix: Add: 'slots are walked by date, then start, then slot index, and assignment ids follow that walk; the open requests on assignments 1–5 are requested, accepted, requested, accepted, requested'.

7. stories/US-scheduling-004.md line 15 [cosmetic] — Problem: The quantitative arm measures 'the p95 server-side response time of the board operation' over '50 sequential calls through the in-process test client' — two different timer boundaries (inside the handler versus around the client call, which includes serialisation). The round-2 disposition's wording, 'wall-clock around each call', was not carried into the arm. The arm otherwise carries every required parameter and is timing-tier, reported never gating, so no gate depends on it. Fix: Replace 'the p95 server-side response time of the board operation' with 'the p95 of the wall-clock duration around each call of the board operation'.

8. stories/US-scheduling-003.md line 12 [cosmetic] — Problem: Arm 2 names the row fields of the unfilled_slots refusal (shift id, date, start, unfilled count) but not the name of the field that carries the rows, and the cross-cutting refusal shape ('the extra fields a story names') relies on the story to name it. The test asserts the rows, so the outcome is unchanged whatever the contract designer calls it. Fix: Name the field in arm 2 and R-scheduling-03, e.g. 'the refusal carries unfilled: a list of {shift_id, date, start, unfilled} rows'.
