# DESIGN-REVIEW-3 — Team Rota
2026-11-07 · convened by the pm-lead · reviewers: architect, developer (parallel, independent, fresh contexts; a workflow of two agents, structured findings graded blocking or cosmetic) · inputs: design/PRODUCT-DESIGN.md v1.2, stories/ (22 stories, 107 arms), design/domains/*/spec.md v1.2, design/INTERFACE-REQUESTS.md (IR-01..11)

## Architect
1. design/INTERFACE-REQUESTS.md line 15 [BLOCKING] — Problem: IR-08 obliges scheduling to emit week_published 'with the recipients', and R-notifications-01 (notifications/spec.md line 7) fixes those recipients as 'every active Member of any role' inside a self-contained payload the Notifier never reads back. Scheduling cannot compute that set: its assignment rows name only assigned members, and its only declared need from identity, IR-06 (line 13; scheduling/spec.md line 18), answers per named member (active, role, name) — there is no interface that enumerates the team. The same need was settled for swaps (IR-09: 'the eligible deciders') but not for scheduling. The publish implementer must choose between a new identity protocol method the contract unit never stubbed, having the Notifier enumerate members (contradicting the self-contained-payload rule and IR-04's narrowing), or having the API layer compose the recipient list — three materially different shapes. Fix: Add a row (IR-12, from scheduling, to identity): 'the ids of every active Member of any role, for week_published recipients' (story US-notifications-001), or extend IR-06 with 'and the list of active member ids'; mirror it in scheduling/spec.md 'Interfaces this domain needs from others'.

2. design/PRODUCT-DESIGN.md line 14 [cosmetic] — Problem: The refusal precedence orders seven buckets but says nothing about order within a bucket, and several arms collide inside one bucket on inputs a test can plausibly build: US-identity-003 last_admin vs future_assignments (both state; the R-scheduling-09 fixture assigns the admin round-robin, so deactivating that admin hits both); US-scheduling-002 already_assigned vs overlapping_shift vs shift_full on a one-slot shift the member already holds; US-identity-004 member_inactive vs invalid_credentials for an inactive member with a wrong passcode (also a disclosure choice: whether account status is revealed without the passcode). Each arm's own test is a single-failure case, so no arm's outcome changes. Fix: Append to the Refusals rule: 'within a bucket, checks run in the order the story's arms list them'; and in US-identity-004 state explicitly whether credentials are verified before the active check (recommended: yes, so member_inactive is only ever answered to a correct passcode).

3. design/domains/notifications/spec.md line 7 [cosmetic] — Problem: R-notifications-01 says 'the Notifier never reads back' while R-notifications-03 (line 9) has the Notifier ask identity whether each recipient is active (IR-04). Both are intended, but the sentence as written forbids the one read the next rule requires. Fix: Reword to 'the Notifier never reads the emitting domain back; its only read is IR-04'.

4. design/domains/swaps/spec.md line 13 [cosmetic] — Problem: R-swaps-07 enumerates four caller refusal codes and says counterpart_overlap and counterpart_inactive are 'recorded as refusal reasons by the system', so Decision.reason (PRODUCT-DESIGN line 84) actually admits six values and is absent on an approved decision — neither the nullability nor whether a caller who sends counterpart_overlap gets invalid_reason is stated. Related shape choice left to the contract: approve and refuse as one decide operation with an outcome or as two operations; either satisfies every arm. Fix: State: 'Decision.reason is absent on approved; on refused it is one of fairness, coverage, policy, other (from the caller — any other value is invalid_reason) or counterpart_overlap, counterpart_inactive (set only by the system)'; name the operation shape once in the story.

5. design/PRODUCT-DESIGN.md line 16 [cosmetic] — Problem: The id tiebreak ('ascending for oldest-first lists, descending for newest-first') presumes ids that increase with creation order, but no entity row says ids are store-assigned sequential integers. With UUIDs the tiebreak is still a deterministic total order, so every arm's assertion holds, but it no longer means oldest-first. Fix: Add to the Entities preamble: 'ids are integers assigned by the store in creation order'.

6. design/INTERFACE-REQUESTS.md line 14 [cosmetic] — Problem: IR-07 has swaps apply the deadline before answering, which needs each request's shift start instant; the only declared path is IR-01 back into scheduling, so the board read re-enters scheduling from inside scheduling's own call. The cycle is accepted and both shapes satisfy the arms, but the protocol signature differs (scheduling passes {assignment_id, start_instant} pairs vs. swaps calls IR-01 per request). Fix: State in IR-07 that scheduling passes the assignment ids with their start instants and swaps applies the deadline to those (no re-entrant IR-01 call).

7. stories/US-identity-005.md line 11 [cosmetic] — Problem: Whether the operator's seed emits member_added is unstated. J-01 distinguishes seeding (#1) from adding (#2) and US-notifications-006 arm 1 covers 'an added member'; the E2E arm (US-swaps-003 arm 11) asserts each party's notifications 'exactly', and the seeded admin is typically a decider, so the count differs by implementation. Decidable, since the seed and the E2E live in the same product, but a seam between identity and notifications that one sentence settles. Fix: Add to the arm: 'the seed emits no notification'.

8. stories/US-identity-002.md line 11 [cosmetic] — Problem: Changing a member to the role they already hold, and changing the role of an inactive member, are unaddressed: whether the first is a no-op, is refused, or emits role_changed (US-notifications-006 arm 2 says 'whose role changed'); the second's notification is already suppressed by R-notifications-03 but the change itself is not ruled on. Fix: Add an arm: 'a change to the role the member already holds changes nothing and emits nothing; an inactive member's role may be changed and nobody is notified' (or refuse both with a named reason).

9. design/PRODUCT-DESIGN.md line 14 [cosmetic] — Problem: The refusal shape {reason, detail, extra fields} names no HTTP status mapping, so the contract designer picks one per reason; and the rule 'an identifier that names nothing is refused not_found' carries no exception for sign-in, whose unknown email is invalid_credentials by US-identity-004 arm 2 (the arm wins, but the rule should say so). Every arm asserts the reason, so any consistent mapping satisfies them. Fix: State once: unauthenticated 401, forbidden 403, not_found 404, every other refusal 409 (or 422 for validation — choose one); add 'except sign-in, where an unknown email is invalid_credentials' to the not_found sentence.

10. design/domains/scheduling/spec.md line 15 [cosmetic] — Problem: R-scheduling-09 says members are 'assigned round-robin by the seeded generator' and that the fixture 'differs for another seed'. Round-robin is deterministic, so the rule does not say what the seed varies (synthetic names and emails, the counterparts drawn, both?), which is what the 'differs for another seed' test must assert. Fix: State what the seed drives: 'the generator draws the synthetic names and the counterparts; the slot assignment is round-robin over members in id order'.

11. stories/US-swaps-001.md line 18 [cosmetic] — Problem: The swap-request-form must know which assignment it is for, but no anchor or route carries it from the Week board (the holder-row has no request control in the Screens table). The UI implementer can decide, and no arm depends on the path. Fix: Add a holder-row control anchor (e.g. holder-swap, shown to the holder only, while the week is published and the deadline has not passed) to the Week board row of the Screens table and to this arm.

## Developer
1. stories/US-scheduling-003.md line 14 [BLOCKING] — Problem: Publishing a week that is already published is unsettled. Arm 1's precondition is 'a draft week'; arm 4 and R-scheduling-04 (design/domains/scheduling/spec.md line 10) enumerate exactly which actions a published week refuses — creating a shift, assigning, unassigning — and omit publish, and no arm or rule names a reason for it. Because the enumeration is explicit, the omission reads as deliberate rather than inferable, and an implementing session must choose between (a) refusing with week_published, (b) succeeding as a silent no-op, or (c) succeeding and re-emitting week_published to every active member (IR-08), which sends the whole team a second notification per repeat. The contract designer cannot enumerate the publish operation's refusal reasons without deciding this. Not raised in DESIGN-REVIEW-1 or -2. Fix: Add to US-scheduling-003 arm 4 and to R-scheduling-04: 'publishing a week that is already published is refused with reason week_published; nothing is emitted' (state bucket, consistent with the other published-week refusals). If idempotent success is preferred instead, say so and state that no week_published event is emitted on a repeat.

2. design/INTERFACE-REQUESTS.md line 13 [cosmetic] — Problem: IR-08 has scheduling emit week_published 'with the recipients', and R-notifications-01 defines them as 'every active Member of any role' — a list scheduling must produce since payloads name people, never selectors. But IR-06, scheduling's only need from identity, is a per-member lookup ('whether a member is active, their role, and their name'); no IR gives scheduling the team's members. The preamble says every cross-domain call goes through a protocol the contract unit creates from this table, so the contract designer would have to add an unrequested method. Only one shape is consistent with R-notifications-01, so this is a gap rather than a fork. Fix: Extend IR-06 (or add IR-12, from scheduling to identity): 'the ids of every active member, for week_published's recipients' — Story: US-notifications-001; mirror it in the scheduling spec's 'Interfaces this domain needs'.

3. design/domains/notifications/spec.md line 7 [cosmetic] — Problem: R-notifications-01 says 'the Notifier never reads back — every payload is self-contained', while R-notifications-03 (line 9) has the Notifier ask identity whether each recipient is active (IR-04). Through the product paths the recipients are the same either way, because the payloads already name only active members; but a unit test of the Notifier fed a payload naming an inactive member passes under one rule and fails under the other, and the Notifier protocol either has an identity dependency or it does not. Fix: State in R-notifications-01 'never reads back the event's data; its one lookup is IR-04 (R-notifications-03)', or drop the IR-04 lookup and make the emitters alone responsible for naming active recipients, keeping member_deactivated as the one emitter-side exception.

4. stories/US-scheduling-006.md line 14 [cosmetic] — Problem: 'no HTTP route performs a transfer (asserted against the served route table)' has no checkable predicate. A route table carries paths, methods and operation ids, not what a handler does, so the only test that can be written is name-based ('no path or operationId contains transfer'), which proves nothing about behaviour and passes under any other name — the arm is close to vacuous as worded. Same wording in R-scheduling-08 (design/domains/scheduling/spec.md line 14). No behaviour fork; a test-design gap. Fix: Either name the predicate — 'the contract's operation ids include no transfer operation, and no module under the API layer imports scheduling's transfer function (a layering-ratchet assertion)' — or drop the arm and rely on arm 1 ('called directly in scheduling's tests') plus R-scheduling-08.

5. design/PRODUCT-DESIGN.md line 14 [cosmetic] — Problem: The refusal precedence names seven buckets but assigns no reason code to a bucket. request_open, already_assigned, shift_full, overlapping_shift, member_inactive (on assign), last_admin, future_assignments and unfilled_slots can each be read as state or validation, and pairs inside one bucket have no order: last_admin vs future_assignments on deactivation, and member_inactive vs invalid_credentials at sign-in — where checking active before verifying the passcode reveals that an inactive account exists, which 'one reason for both' (US-identity-004 arm 2) was written to prevent. No arm exercises two simultaneous failures, so no arm's outcome changes; the contract designer picks. Fix: Give each reason its bucket in the specs' Testable-as column (e.g. 'request_open (state)'), and add to R-identity-06: 'credentials are verified before the active check, so an inactive member with a wrong passcode is refused invalid_credentials'.

6. stories/US-identity-001.md line 15 [cosmetic] — Problem: 'ordered by name then id' — the cross-cutting tiebreak rule (PRODUCT-DESIGN line 16) fixes the id direction only for oldest-first and newest-first lists; a name-sorted list has no stated direction, and name collation (case-sensitive or not) is unstated, so a test with 'avi' and 'Bob' or two equal names cannot be written from the arm alone. Fix: Write 'ordered by name (compared case-insensitively) then id ascending' in arm 5 and R-identity-09.

7. stories/US-swaps-003.md line 21 [cosmetic] — Problem: Arm 11 (the brief's §6 path in the browser, on every commit) needs every domain's API and UI and the CI wiring, so the swaps decide unit cannot close at its own layer until the last UI unit exists; the story is a domain story and the product's acceptance in one. Round-2 D13 placed the §6 test here deliberately, so this is a sequencing concern, not a contradiction. Fix: Move arm 11 to its own cross-cutting story (e.g. US-product-001 'the brief's path runs on every commit') that the plan cuts as the final unit, or state in the arm that the plan places it in the packaging/E2E unit while US-swaps-003's other arms close earlier.

8. design/PRODUCT-DESIGN.md line 65 [cosmetic] — Problem: US-notifications-005 arm 2 (line 12) invokes mark-read 'from a notification-item control', but the Notifications screen's anchors are notification-list, notification-item, notification-empty — no anchor for the control the UI test must find. Fix: Add notification-mark-read to the Notifications screen's anchors and name it in arm 2.

9. design/PRODUCT-DESIGN.md line 63 [cosmetic] — Problem: The Swap request screen has no entry point: nothing names how a member reaches swap-request-form for one of their own holder-rows on the board, nor the anchor the UI test clicks, and the form must know which assignment it is for. The Week board's anchors (line 62) have no request control either. Fix: Add holder-request-swap to the Week board anchors (shown on the caller's own holder-rows of a published week while now < the deadline) and state in US-swaps-001 arm 8 that it opens swap-request-form for that assignment.

10. stories/US-swaps-004.md line 11 [cosmetic] — Problem: The member's request list carries state, answer_reason, the decision and the party awaited, but not the shift's date and start or the other party's name, so the inbox would list requests without saying which shift or whom — against the North Star's 'plainly'. IR-01 and IR-09 already supply both; an implementation would likely add them, but the arm and the contract would not require it. Fix: Add 'each with its shift's date and start and the other party's name' to arm 1 (and to US-swaps-005 arm 1 for deciders), and list US-swaps-004/005 in IR-01's and IR-09's Story column.

11. stories/US-scheduling-004.md line 15 [cosmetic] — Problem: The timing arm carries statistic, threshold, n, seed, tolerance, pass predicate and fixture, but not the call itself: which start_date (with the fixture's clock at 2026-11-05 and the week at 2026-11-09, the 'current week' is none, so the board must be called by start_date), whether mine is set, and which caller's token. A session picks; the number moves little, but the measurement is not reproducible from the arm alone. Fix: Append 'called by the fixture's start_date with mine unset, as the fixture's admin' to the arm.
