# DESIGN-REVIEW-7 — Team Rota
2026-11-07 · convened by the pm-lead · reviewers: architect, developer (parallel, independent, fresh contexts; a workflow of two agents, structured findings graded blocking or cosmetic) · inputs: design/PRODUCT-DESIGN.md v1.6, stories/ (22 stories, 109 arms), design/domains/*/spec.md v1.6, design/INTERFACE-REQUESTS.md (IR-01..12), OPEN-QUESTIONS.md (Q-01..03)

## Architect
1. design/PRODUCT-DESIGN.md line 14 [cosmetic] — Problem: The Refusals rule says a target identifier that fails shape is refused invalid_request 'at the not_found step' (so after unauthenticated and forbidden), but the lenient read it prescribes is stated for the body only ('the API layer reads the body leniently'). Target ids travel in the path or query; a typed path parameter in the chosen stack is rejected by the framework before any dependency runs, so a tokenless caller sending a malformed assignment id would get 422 instead of 401, and a member calling decide with a malformed request id would get 422 instead of forbidden — contrary to the stated precedence. The behaviour is settled by the rule; what is missing is the sentence that tells the contract designer to declare target ids so the API layer can read them leniently (or the implementer to parse them by hand). No arm tests a malformed id, so no outcome changes. Fix: Extend the sentence to 'the API layer reads the body, path and query leniently', and add to the contract note that a target id in the path or query is declared so that its shape is checked by the API layer at the not_found step, not by the framework before the caller is resolved.

2. design/PRODUCT-DESIGN.md line 14 [cosmetic] — Problem: Sign-in is the one operation outside the token chain, and its precedence for an unreadable body has to be inferred from three general clauses: a missing or wrong-typed email is a target field failing shape, so invalid_request at the lookup step; a missing passcode with a known email is a non-target field, so the 401 bucket is answered first and the result is invalid_credentials (the missing passcode is not the passcode). That is derivable and consistent with 'credentials are verified before the active check', but counter-intuitive (a missing passcode answers invalid_credentials, not invalid_request) and nowhere stated for sign-in itself, whose (code, status) list the contract carries separately. Fix: Add one sentence to the sign-in exception: 'at sign-in, a body whose email cannot be read is invalid_request; otherwise credentials are verified as sent (a missing passcode is invalid_credentials), then the active check (member_inactive)'.

3. design/PRODUCT-DESIGN.md line 18 [cosmetic] — Problem: The success response of every write operation outside swaps is unnamed: add member, change role (including the same-role no-op), deactivate, create shift, assign, unassign, publish and mark-read. Swaps names its row (R-swaps-09) and every list names its fields, so a contract designer will return the created or changed entity as its list shows it, and no arm's outcome depends on the choice — but it is a choice the contract makes silently eight times. Fix: Add a cross-cutting bullet: 'Every write returns the entity it created or changed, in the shape its list shows it: a member row of R-identity-09; a shift with its holder-rows as the board shows it (create, assign, unassign); the week {start_date, state} (publish); the notification item (mark read). The same-role no-op returns the unchanged member row with status 200.'

4. stories/US-scheduling-004.md line 14 [cosmetic] — Problem: The weeks-list operation returns the listed weeks 'together with the current week ... or none', but the field that carries the current week is not named and its representation (the start_date key, or the full {start_date, state} row, or null when none) is left to the contract. Either representation satisfies the arm and the sign-in landing arm (US-identity-004 arm 5), so this is a shape detail, not a guess between behaviours. Fix: Name it in the arm and in R-scheduling-06: '{weeks: [{start_date, state}], current: the start_date of the current week, or null}'.

5. design/INTERFACE-REQUESTS.md line 13 [cosmetic] — Problem: IR-06's Story column lists US-scheduling-002 and US-scheduling-004 only, yet the transfer (US-scheduling-006, 'Member (read through identity's interface)') reads 'whether a member is active' through the same row to answer counterpart_inactive, and the scheduling spec's needs-line (line 18) cites IR-06 for it. Traceability only; the interface itself is complete. Fix: Add US-scheduling-006 to IR-06's Story column.

6. design/INTERFACE-REQUESTS.md line 4 [cosmetic] — Problem: The cycles paragraph says 'the plan names the build and retire order (INTERFACES.md, "Build order")', but design/INTERFACES.md is still the v0.1 template with Protocols and Traceability sections only; no 'Build order' section exists. The pointer is forward to the contract unit's output, so nothing is contradicted, but as written it names a section a reader cannot find. Fix: Either reword to 'to be named by INTERFACES.md's Build order section, written by the contract unit' or have the contract unit add that section when it writes the protocols, with the Null-implementation retire order per cycle (identity↔scheduling, scheduling↔swaps, identity↔notifications).

## Developer
1. stories/US-identity-001.md line 15 [cosmetic] — Problem: Arm 5's clause "an operation naming a member id that names nobody is refused not_found" (placed here by DESIGN-REVIEW-6 A7) is unreachable within this story's own two operations: add member takes no member id and list members takes none. The operations that do take a member id are change role (US-identity-002), deactivate (US-identity-003) and assign (US-scheduling-002, via IR-06), and none of those stories' arms names not_found, so a cutter that cuts tests from arms produces no not_found test for them; R-identity-08's "each story's tests cover them for its own operations" is prose. The behaviour itself is settled by the cross-cutting rule (not_found, 404), so nothing is guessed between behaviours; the clause is misplaced and the coverage it was meant to give is absent. The same absence holds for unassign (assignment id), the board (a start_date with no week), the request (assignment id), answer and decide (request id) and mark-read (notification id): only publish (US-scheduling-003 arm 3) and the counterpart id (US-swaps-001 arm 6) name not_found. Fix: Move the clause out of US-identity-001 arm 5 into US-identity-002 ("a member id that names nobody is refused not_found" on a role change) and US-identity-003 (the same on a deactivation), and add one not_found clause to the arm of each other operation that looks something up: US-scheduling-002 (shift id or member id on assign; assignment id on unassign), US-scheduling-004 (a start_date with no week), US-swaps-001 (assignment id), US-swaps-002 and US-swaps-003 (request id), US-notifications-005 (notification id).

2. stories/US-scheduling-003.md line 12 [cosmetic] — Problem: "the refusal carries unfilled: a list of {shift_id, date, start, unfilled} rows in board order" (and R-scheduling-03, design/domains/scheduling/spec.md line 9) does not say whether a fully filled shift gets a row with unfilled 0. The field's name and arm 6's "the unfilled_slots refusal lists the shifts" make rows-only-for-shifts-with-an-empty-slot the dominant reading, and the reason and status (unfilled_slots, 409) are identical either way, so an implementation decides it without changing an arm's outcome; but a test written as an exact list against a fixture holding one full and one unfilled shift would disagree with an implementation that read it the other way. Fix: State it once in arm 2 and in R-scheduling-03: "one row per shift with at least one empty slot (unfilled >= 1), in board order; a full shift has no row".

3. design/PRODUCT-DESIGN.md line 14 [cosmetic] — Problem: Three outcomes of the Refusals rule are determinable only by chaining sentences: (a) a missing field that has a named validation code (role, slots, start_date, date, start, end, reason) is answered with that code and not invalid_request, which follows from "declared optional in the schema" plus "always the answer for its field", while a wrong-typed value of the same field (reason: 42) is invalid_request because it "cannot be read"; (b) invalid_request answered "at the not_found step" for a malformed target id keeps the status of its bucket (422), not of the step (404); (c) at sign-in, which has no not_found step and whose email and passcode carry no named code, a body missing either is invalid_request (a body that cannot be read) rather than invalid_credentials. Each is decidable from the text and no arm builds these inputs, but the contract unit must state every operation's (code, status) pairs and will otherwise rediscover each by reasoning. Fix: Add one sentence after "invalid_request precedes every other code": "A missing field with a named validation code is answered with that code (reason_required for reason; invalid_role, invalid_slots, not_week_start, outside_week, invalid_interval for theirs); a wrong-typed one is invalid_request; invalid_request carries 422 wherever in the order it is answered; at sign-in a body missing email or passcode is invalid_request."

4. design/PRODUCT-DESIGN.md line 2 [cosmetic] — Problem: The header's list after "v1.6 `design/DESIGN-REVIEW-6.md` (21, one blocking; the developer agreed):" — "the caller resolved once, refusal shape and precedence, not_found, the typed Notifier events, 'open' defined once, the answer fields, list members and list weeks, the badge per holder, tiebreaks, ids on every entity" — is v1.2's change list (VERSIONS.md line 40), not v1.6's, which VERSIONS.md line 72 records as the lenient body read, invalid_request first within validation and the completed Reason codes table. The first line every session reads misdescribes what the current version changed; no rule or arm is affected. Fix: Replace the colon list with v1.6's own ("lenient body read; invalid_request first within validation; the Reason codes table completed: repeated deactivation, counterpart_overlap at request, the seed's exit status") or drop the per-version lists from the header and point at VERSIONS.md, which is the authority.

5. design/PRODUCT-DESIGN.md line 93 [cosmetic] — Problem: The Entities table lists Role as an entity of the identity domain with key field "name", while the Ids rule (line 17) says Role is an enumeration carried in Member.role and not a stored row, and US-identity-001/002/005 list Role under "Data touched ... (owned)". A data-model unit reading the Entities table as the list of rows to create would build a roles table the Ids rule forbids; the Ids rule settles it, so nothing material is guessed, but the two lines disagree in the one document both units read. Fix: Rewrite the row as "Role | identity | an enumeration (admin, planner, member) carried in Member.role; not a stored row | —" (or delete it), and drop Role from the stories' data lists, leaving Member.

6. design/INTERFACE-REQUESTS.md line 16 [cosmetic] — Problem: IR-09 names "the eligible deciders (active admins and planners)" while US-notifications-003 arm 1 and R-notifications-01 use "eligible decider" for "every active admin and planner who is not a party". The party exclusion is swaps' own rule (R-swaps-05), so the recipient set of swap_accepted is settled, but the same word names two sets across the interface boundary and the protocol designer must notice which side removes the parties. Fix: Reword IR-09: "every active admin and planner (swaps removes the parties, R-swaps-05, before naming swap_accepted's recipients)", and use "eligible" only for the post-exclusion set.

7. design/domains/scheduling/spec.md line 15 [cosmetic] — Problem: R-scheduling-09 says the seed varies only the synthetic names, emails and counterparts, but leaves the fixed remainder unstated: which ids are the admin and the two planners (presumably 1 and 2–3, since the seed command creates the admin first and add member the rest), the reason code of the five open requests, and the passcode the timing arm signs the admin in with. The fixture is reproduced byte for byte by one implementation whatever it chooses, and the timing arm's call does not depend on these, so no behaviour is guessed; a second implementation would not reproduce the first's fixture. Fix: Add to R-scheduling-09: "member 1 is the admin, 2–3 the planners, 4–12 members; every request's reason is other; passcodes are drawn by the generator and exposed by the fixture with the admin's token".

8. stories/US-notifications-005.md line 12 [cosmetic] — Problem: Marking a notification that is already read has no outcome stated: no code for it exists in the Reason codes table (the only notifications code is not_recipient), so the only consistent reading is that it succeeds and changes nothing, but neither arm 2 nor R-notifications-04 says so, and every other repeated action in this design is explicitly refused (publish again, assign twice, deactivate twice, seed twice) or explicitly a no-op (role already held). Fix: Append to arm 2: "; marking it again changes nothing and succeeds", and the same clause to R-notifications-04.

9. design/PRODUCT-DESIGN.md line 17 [cosmetic] — Problem: The success answer of identity's add, change role and deactivate, scheduling's create shift, assign, unassign and publish, and notifications' mark-read is unstated; swaps' answers are fixed by R-swaps-09, and sign-in, the board and every list by their arms. Every arm of the unstated operations verifies through the team list or the board, so the contract designer decides the bodies without changing any arm's outcome; the shapes are nonetheless invented at the contract unit rather than read. Fix: Add one line beside the Ids rule: "A successful operation answers the row it created or changed, with the fields its list or board shows (a member as the team list shows it; a shift, an assignment or the week as the board shows them); unassign answers nothing".

10. stories/US-scheduling-001.md line 17 [cosmetic] — Problem: A week comes into being with its first shift and week-picker offers only listed weeks, so the only way a planner can begin a new week from the Week board is a shift-create form that takes start_date itself; arm 7 says only "the shift-create form submits". Arm 1 names start_date among the inputs, so the UI unit can decide it and no outcome changes, but the arm that drives the form does not say the form carries the week. Fix: Reword arm 7: "the Week board's shift-create form takes start_date, date, start, end and slots — so a new week is begun from it when none is selected — submits, and the shift appears on week-board in date and start order".

VERDICT: AGREED
