# DESIGN-REVIEW-6 — Team Rota
2026-11-07 · convened by the pm-lead · reviewers: architect, developer (parallel, independent, fresh contexts; a workflow of two agents, structured findings graded blocking or cosmetic) · inputs: design/PRODUCT-DESIGN.md v1.5, stories/ (22 stories, 108 arms), design/domains/*/spec.md v1.5, design/INTERFACE-REQUESTS.md (IR-01..12), OPEN-QUESTIONS.md (Q-01..03)

## Architect
1. stories/US-identity-003.md line 11 [BLOCKING] — Problem: No arm or rule names the outcome of deactivating a member who is already inactive, an input a test builds by calling deactivate twice. future_assignments and last_admin cannot fire for an inactive member (they hold no future assignment and are not an active admin), so nothing else decides it, and three readings stay open: (a) a silent no-op, following R-identity-01's precedent for a role already held ('changes nothing and emits nothing'); (b) a 200 that sets active=false again and re-emits member_deactivated, writing a second notification to the inactive member, which R-notifications-03's exception lets through, so the Notifier will not drop it; (c) a refusal, which is how every other repeated action in this design is answered (publish again: week_published; assign twice: already_assigned; seed twice: team_not_empty; second request: request_open; answer or decide twice: wrong_state) but needs a code the deactivate operation does not list. The contract's (code, status) list for deactivate and the count of member_deactivated notifications differ between the readings, so an implementing session must guess. Fix: Add an arm to US-identity-003 and a clause to R-identity-04 (design/domains/identity/spec.md line 10). Recommended, following the design's dominant pattern for repeats: 'deactivating a member who is already inactive is refused with reason member_inactive (409 on this operation, as on assign); nothing is emitted', and add the pair to the status-per-operation note under the Reason codes table. Alternatively mirror R-identity-01 exactly: 'changes nothing and emits nothing'. Either settles it; whichever is chosen must say that no second member_deactivated is written.

2. stories/US-swaps-001.md line 16 [cosmetic] — Problem: R-swaps-08 admits as counterpart anyone active, not the requester and not holding a slot on that shift; a shift the counterpart holds on the same date whose [start, end) intersects the requested one (R-scheduling-02) is checked only by the transfer at approval (counterpart_overlap, US-scheduling-006 arm 2). So a request naming such a counterpart is offered by the swap-request-form (which composes eligibility from the same three facts), accepted by the server, notified, accepted by the counterpart, listed for decision, and can only end in a system refusal. The design is consistent (the truth is shown, and the requester may request again before the deadline since a refused request is not open), but it is a guaranteed-to-fail path through four parties. Fix: Either add counterpart_overlap to R-swaps-08's order at request time (after counterpart_on_shift), with IR-01 also returning the counterpart's same-date intervals so the form can exclude them; or record it as a purpose question beside Q-02 and Q-03 for the operator. Not blocking: no arm contradicts another and no shape is in doubt.

3. design/domains/swaps/spec.md line 15 [cosmetic] — Problem: R-swaps-09 lists 'party (per viewer)' without a type. The arms need only a mark (US-swaps-005 arm 2: rows the viewer is party to are marked swap-party) and the viewer knows their own id from sign-in, so a boolean suffices, but a contract designer may also read it as requester | counterpart | none. Neither reading changes an arm's outcome. Fix: State the type once in R-swaps-09: 'party: true when the viewer is the requester or the counterpart, else false'.

4. stories/US-scheduling-004.md line 11 [cosmetic] — Problem: Arm 1 fixes the holder-row fields exactly (assignment id, member id, name, pending, requestable) but names no shift-level fields and no week-level state, while the planner's shift-assign control needs slots against the holder count to show a free slot, the overlap display needs end, and 'the board shows the week as published' (US-scheduling-003 arm 6) needs the week's state. All are decidable from the Entities table today, so no outcome changes. Fix: Add to arm 1 and to R-scheduling-05: 'each shift with id, date, start, end, slots and its holder-rows; the board carries the week's start_date and state'.

5. design/PRODUCT-DESIGN.md line 14 [cosmetic] — Problem: Validation is the last bucket and a named code 'is always the answer for its field', so the contract must declare every field with a named code (reason, role, slots, date, start, end) without schema `required` or enum, and the API layer must read the body leniently and defer invalid_request (other than for a target-identifying field) to the validation step: a framework-level body parse would answer invalid_request 422 before not_holder 403 on a non-holder's request carrying reason: 5, against the stated order. The rule itself is deterministic; what is missing is the instruction to the contract unit, which otherwise discovers it at the first precedence test. Fix: Add one sentence after 'never as schema enums': 'fields with a named validation code are declared optional in the schema, and the API layer reads the body leniently so that invalid_request, except for a target-identifying field, is answered at the validation step, last'.

6. design/domains/scheduling/spec.md line 7 [cosmetic] — Problem: 'end after start, never crossing midnight' does not say whether end may be 24:00. A time-of-day type (HH:MM, RFC 3339 partial-time) tops out at 23:59, so an evening shift to midnight must be entered as 23:59; the overlap rule on [start, end) still works and no outcome changes, but the first real team will ask. Fix: State 'end is at most 23:59' in R-scheduling-01 and US-scheduling-001 arm 4, or admit 24:00 explicitly together with the contract's time format.

7. design/INTERFACE-REQUESTS.md line 13 [cosmetic] — Problem: IR-06 and IR-09 answer 'whether a member is active, and their name'. Assign (unknown member id: not_found before member_inactive) and request (unknown counterpart: not_found before counterpart_inactive) need the protocol to distinguish 'no such member' from 'inactive', or the consumer cannot answer not_found at the not_found step as the cross-cutting rule requires. The rule fixes the outcome; the protocol only has to carry it, so the Null implementation's signature should say so. Fix: Say in IR-06 and IR-09, and in INTERFACES.md when the protocols are written: 'absent for an id that names no member; the consumer answers not_found'.

## Developer
1. design/domains/swaps/spec.md line 15 [cosmetic] — Problem: R-swaps-09 lists 'party (per viewer)' with no values, while every other row field has its values stated (awaiting: counterpart | decider | none; decision: {...} or absent). US-swaps-005 arm 2 ('rows the viewer is party to are marked swap-party') and US-swaps-004 arm 1 only need 'is the viewer a party', and the browser already has the viewer's id and both party ids, so a boolean is the only reading that adds nothing — but the contract designer settles the type by inference rather than by text. Fix: Write the values once in R-swaps-09: 'party: true when the viewer is the requester or the counterpart, else false (per viewer, computed by the server)'; echo the same words in US-swaps-005 arm 2.

2. design/PRODUCT-DESIGN.md line 14 [cosmetic] — Problem: invalid_request sits in the validation bucket but appears in no story arm, so the within-bucket tiebreak ('the order the story's arms list them') cannot place it against reason_required / invalid_reason / invalid_role on a double-fault body such as answer {outcome: 'maybe', reason: 'bogus'} or add-member {role: missing, email: 'x'}. The rule's own definition ('a body that cannot be read into the operation's fields') implies it must come first within validation — nothing else about the body can be judged — and the status is 422 either way, so no arm's outcome changes; but it is unstated. The same sentence also implies, by state-before-validation, that {email: duplicate, role: missing} answers duplicate_email, which obliges the API layer to read the body field by field rather than through a strictly typed model; that consequence is nowhere said. Fix: Add one clause: 'within the validation bucket invalid_request precedes every other code, since a body that cannot be read admits no other check of its fields' — and, if the lenient-parse consequence is intended, say so in one line ('the API reads the body leniently so that earlier buckets are answered before a missing or wrong-typed non-target field'); if it is not intended, generalise the A7 clause so that any unreadable field is answered invalid_request at the not_found step.

3. design/PRODUCT-DESIGN.md line 31 [cosmetic] — Problem: The footnote names week_draft and member_inactive as the codes that appear in two buckets, but counterpart_inactive also appears twice: state 409 on the request (line 26, US-swaps-001 arm 6) and 'internal, never an HTTP refusal' on the transfer (line 29, US-scheduling-006 arm 3, surfaced as Decision.reason). The rows themselves are unambiguous, so the contract is not affected. Fix: Extend the parenthetical: '…; counterpart_inactive: 409 on a request, internal on the transfer'.

4. stories/US-identity-004.md line 15 [cosmetic] — Problem: The Screens table (design lines 74, 77, 78) lists sign-in-form, sign-in-email, sign-in-passcode, sign-in-submit, swap-reason, swap-submit and swap-inbox, but no story arm names any of them: US-identity-004 arm 5 says 'the sign-in screen's form submits' and US-swaps-001 arm 8 says 'the swap-request-form … submits' without the field and submit anchors, and no arm names swap-inbox although six arms say 'the inbox'. A UI test author takes the anchors from the table, so nothing is guessed, but the stories' own rule that anchors are named per arm is not met for these seven. Fix: Name the anchors in the arms that drive them: US-identity-004 arm 5 'the sign-in-form's sign-in-email and sign-in-passcode submit via sign-in-submit and land …'; US-swaps-001 arm 8 '… swap-reason and swap-submit … the swap-inbox shows the new request …'.

5. design/domains/notifications/spec.md line 8 [cosmetic] — Problem: R-notifications-02's 'Testable as' says 'for each event the payload fields appear in the text', which read literally requires request_id and member_id (payload fields of every swap and identity event) to appear in the notification text; the story arms it serves (US-notifications-002/003/004/006) name narrower sets (date, start, names, reason, role). The arms govern and no implementer would print ids, but the spec column over-claims what the tests assert. Fix: Reword the column: 'for each event, the payload fields the story's arm names appear in the text; ids are carried, not shown'.

6. design/domains/notifications/spec.md line 7 [cosmetic] — Problem: Six of the nine event payloads carry a 'recipient(s):' gloss; member_added{member_id, role}, role_changed{member_id, role} and member_deactivated{member_id} carry none, so the recipient is inferred from US-notifications-006 rather than read from the rule that claims to name 'exactly the people the emitting domain names in the payload'. Fix: Add '; recipient: the member (member_id)' to each of the three identity events, matching the form of the other six.

7. design/PRODUCT-DESIGN.md line 16 [cosmetic] — Problem: 'Every list … breaks ties by id' cannot apply to the weeks list (US-scheduling-004 arm 4, 'newest first by start_date'): Week has no integer id (line 17) and start_date is its unique key, so no tie is possible. Harmless, but a contract or test author checking the rule against each list finds one it does not fit. Fix: Append to the rule: '(the weeks list, keyed by start_date, cannot tie)'.

8. design/PRODUCT-DESIGN.md line 26 [cosmetic] — Problem: team_not_empty is listed in the state bucket with status 409, but the only operation that answers it is the operator's seed command, which is outside the API (US-identity-005, Permissions line 112) and has no HTTP status; line 31 says the contract lists each operation's (code, status) pairs, and the seed is in no contract. Fix: Mark it in the table: 'team_not_empty (seed command; exit status, no HTTP)'.

9. stories/US-scheduling-002.md line 17 [cosmetic] — Problem: Arm 7 says 'a member calling the action is refused with reason forbidden' in a story with two actions (assign, arm 1; unassign, arm 6). Permissions line 117 denies both to members, so the outcome is settled, but a test author reading the arm literally covers only one. Fix: Reword: 'a member calling assign or unassign is refused with reason forbidden'.

10. stories/US-identity-001.md line 28 [cosmetic] — Problem: Two stories openly carry two operations with different audiences: US-identity-001 bundles 'add a member' (admin; arms 1–4, 6) with 'list members' (every role; arm 5), which the story's own note acknowledges; US-scheduling-004 bundles the board with 'list weeks and the current week' (arm 4), a separate Permissions row (line 116). Both are declared, not secret, and both land in the same domain unit, so nothing is guessed — but each story's 'roles' and 'persona' describe only one of its halves. Fix: Either leave as is (acceptable) or split 'list members' into US-identity-006 (J-01#2, roles [admin, planner, member]) and 'list weeks' into its own arm set under a J-03#1 story; if left, add the same acknowledging note to US-scheduling-004's Out of scope as US-identity-001 carries.

11. design/INTERFACE-REQUESTS.md line 8 [cosmetic] — Problem: IR-01 describes the shift as '(id, date, start instant, end, current holder ids)' — start as an instant, end bare — while the request row (R-swaps-09) needs shift_date and shift_start as a date and a time of day, and the deadline needs the start instant. Everything is derivable, but the protocol designer must choose which representation the interface returns. Fix: State both: 'its shift (id, date, start and end as times of day, start_instant, current holder ids)'.

OPEN-QUESTIONS.md line 17 [cosmetic] — Problem: Q-01's resolution says the rule lives in 'the permissions matrix ("allowed (not own)")', but the matrix (PRODUCT-DESIGN line 121) reads 'allowed (not party)' since DESIGN-REVIEW-1 A7 generalised the ruling. A resolved question pointing at wording that no longer exists. Fix: Change the quoted text to '"allowed (not party)"' and note 'generalised by DESIGN-REVIEW-1 A7' as the design's Q-01 row already does.

13. stories/US-swaps-002.md line 13 [cosmetic] — Problem: Arm 3 ('answering a request that is not in state requested is refused with reason wrong_state') and US-swaps-003 arm 5 (the same for accepted) say 'state' without 'stored'; an implementer who tests 'not open' (R-swaps-03's own wording, 'only while the request is open in state requested') answers wrong_state to an expired request and makes the past_deadline arms (US-swaps-002 arm 4, US-swaps-003 arm 6) unreachable, since their only buildable input is an expired request. Design line 18 and the Entities table do say expired is never stored, and the past_deadline arms fail the wrong implementation, so the design settles it — one word would stop the detour. Fix: Insert '(stored state)' in US-swaps-002 arm 3 and US-swaps-003 arm 5, and in R-swaps-03/04's 'Testable as' write 'wrong_state (stored state), then past_deadline (expired)'.

14. design/domains/scheduling/spec.md line 11 [cosmetic] — Problem: R-scheduling-05 defines the board's shift order and the holder-row fields but not the board's top-level fields: the week's start_date and state (needed by board-draft 'Not published yet' and by US-scheduling-003 arm 6 'the board shows the week as published') and the shift's own fields (id, date, start, end, slots). The contract designer takes them from the Entities table, and no arm's outcome depends on the choice. Fix: Add to R-scheduling-05: 'the board is {start_date, state, shifts: [{id, date, start, end, slots, holders: [holder-row]}]}'.
